# 프론트엔드 요구사항 명세

이 문서는 현재 백엔드가 **실제로 제공하는 기능**을 기준으로 작성되었다.
백엔드 수정이 선행되어야 하는 항목은 🚧, 팀이 추후 처리하기로 한 항목은 ⏸ / ⚪ 로 표시했다.

- Base URL: `http://localhost:8090`
- 대상 문서: [[API-개요]], [[화면-정의서]], [[프론트엔드-데이터-모델]]

---

## 0. 선행 조건 (백엔드 수정 필요)

프론트엔드 착수 전에 **반드시** 해결해야 한다.

| # | 항목 | 상태 | 상세 |
|---|---|---|---|
| P-1 | **CORS 설정** | ⏸ 보류 — 개발 프록시로 우회 | [[알려진-이슈]] BE-01 |
| P-2 | Refresh 쿠키 `SameSite`/`Path` | ⏸ P-1과 함께 | [[토큰-저장-전략]] |
| P-3 | `GET /api/user/me` | ⚪ 의도됨, 추후 구현 예정 | [[API-User]] |
| P-4 | **`/error` permitAll** | 🟠 권장 | [[알려진-이슈]] BE-25 |

- **P-1/P-2**: 백엔드 수정 전까지 Vite/Next 프록시로 동일 오리진처럼 개발한다. → [[API-클라이언트-가이드]]
- **P-3**: 프로필 화면(FR-2)은 이 API가 구현된 뒤에 착수한다.
- **P-4**: 미처리 예외가 401 `LOGIN_REQUIRED`로 위장되어 내려온다. 인터셉터가 이를 토큰 만료로 오인해
  **강제 로그아웃**시킬 수 있으므로 재시도 로직에 주의가 필요하다.

## 1. 인증 (FR-1)

### FR-1.1 회원가입

| 항목 | 내용 |
|---|---|
| API | `POST /api/auth/signup` |
| 입력 | 이메일, 비밀번호, 비밀번호 확인, 닉네임 |
| 클라이언트 검증 | 이메일 형식 / 비밀번호 8~30자 / 비밀번호 일치 / 닉네임 필수 |
| 전송 시 주의 | 키가 **`nick_name`** (스네이크). `role`은 항상 `"USER"` 고정 |
| 성공 | 201 → 로그인 페이지로 이동 + "가입 완료" 안내 |
| 실패 | 409 `DUPLICATE_USER_EMAIL` → 이메일 필드에 에러 표시 |

> 서버가 이메일 **형식**을 검증하지 않는다. 클라이언트에서 반드시 검증할 것.
> `role`을 클라이언트가 보낸다는 점은 보안 결함이지만, 프론트엔드는 `"USER"`만 보내면 된다.

### FR-1.2 로그인

| 항목 | 내용 |
|---|---|
| API | `POST /api/auth/login` |
| 입력 | 이메일, 비밀번호(8자 이상) |
| 성공 | `accessToken`(이미 `Bearer ` 포함), `id`, `nickName` 저장 → 메인으로 |
| 실패 | 401 `LOGIN_REQUIRED` → "이메일 또는 비밀번호가 올바르지 않습니다" |
| 쿠키 | `refreshToken` HttpOnly 자동 저장 (JS 접근 불가) |

응답의 `refreshToken` 바디 필드는 **무시**한다.
응답의 `role`은 항상 null이므로 관리자 판별에 쓸 수 없다.

### FR-1.3 소셜 로그인

| 항목 | 내용 |
|---|---|
| API | `GET /oauth2/authorization/kakao`, `/oauth2/authorization/google` |
| 방식 | `window.location.href`로 **전체 페이지 이동** (fetch 불가) |
| 🚧 문제 | 성공 시 서버가 JSON을 그대로 출력한다 → 프론트엔드로 토큰을 넘길 수 없다 |

**해결책**: `OAuth2LoginSuccessHandler`를 프론트엔드 콜백 URL로 리다이렉트하도록 수정.

```java
// 예: 프론트엔드가 토큰을 수신할 수 있게
response.sendRedirect(frontendUrl + "/oauth/callback#accessToken=" + token);
```

프론트엔드는 `/oauth/callback` 라우트에서 토큰을 추출해 저장한다.
→ [[토큰-저장-전략]]

### FR-1.4 로그아웃

`POST /api/auth/logout` → 클라이언트 상태 초기화 → 메인으로.
쿠키가 없어도 200이므로 실패 처리 불필요.

### FR-1.5 토큰 자동 갱신

- Access Token 수명 **1시간**
- 401 응답 수신 시 `POST /api/auth/reissue` 1회 시도 → 성공하면 원 요청 재시도
- 재발급 실패 시 로그인 페이지로 이동
- ⚠️ reissue 응답의 `accessToken`에는 `"Bearer "` 접두사가 **없다** → 정규화 필요

구현은 [[API-클라이언트-가이드]] 참조.

## 2. 사용자 프로필 (FR-2) ⚪ 추후

> 프로필 기능은 백엔드에서 **추후 구현 예정**으로 결정됨. 현 단계에서는 화면을 만들지 않는다.

| 기능 | API | 상태 |
|---|---|---|
| 내 프로필 조회 | `GET /api/user/me` | ⚪ 추후 구현 |
| 프로필 수정 | — | ❌ API 없음 |
| 내가 쓴 글 | — | ❌ API 없음 |
| 비밀번호 변경 | — | ❌ API 없음 |
| 회원 탈퇴 | — | ❌ API 없음 |

**현재 구현 가능한 범위**: 로그인 응답으로 받은 `nickName`을 헤더에 표시하는 정도.

마이페이지를 만들려면 [[API-User]]의 "미구현 API" 목록이 먼저 개발되어야 한다.

## 3. 게시판 (FR-3)

### FR-3.1 게시판 목록

`GET /api/board/all` → `BoardResponse[]`

- 사이드바 또는 상단 탭으로 표시
- 자주 바뀌지 않으므로 클라이언트 캐싱 권장
- 클릭 시 `/boards/{id}` 로 이동

### FR-3.2 게시판 관리 (ADMIN) 🚧

생성/수정/삭제 API는 있으나 **현재 사용자가 ADMIN인지 알 수 없다** (`role`이 항상 null).

임시 대응:
- 관리 기능을 `/admin` 라우트로 분리하고 링크를 노출하지 않는다
- 403이 오면 "권한이 없습니다" 표시

근본 해결: 로그인 응답에 `role`을 채우거나 `GET /api/user/me`에 role을 포함시킨다.

## 4. 게시글 (FR-4)

### FR-4.1 목록

| 항목 | 내용 |
|---|---|
| API | `GET /api/post/{boardId}/all?page=&size=&sort=` |
| 기본 | size 10, `createdAt,DESC` |
| 표시 | 제목, 작성자 닉네임, 조회수, 작성일, 이미지 유무 |
| 페이징 | 번호 페이징 또는 무한 스크롤. `page.number`는 **0-based** |

⚠️ 응답의 `PostDTO`에 **본문 전체가 포함**되어 있다. 목록에서는 렌더링하지 말 것 (성능).
⚠️ 목록에서는 `canEdit`/`canDelete`가 항상 false다.
⚠️ 없는 `boardId`도 404가 아니라 빈 페이지를 반환한다 → 게시판 존재 확인은 `/api/board/all`로.

`GET /api/post/all`(전체 게시글, 페이징 없음)은 화면에서 사용하지 않는다.

### FR-4.2 상세

| 항목 | 내용 |
|---|---|
| API | `GET /api/post/{id}` |
| 표시 | 제목, 작성자, 게시판명, 본문, 조회수, 작성일, 이미지 갤러리 |
| 이미지 | `images[].url`에 `/images/` 접두사 포함 → `${API_BASE}${url}` |
| 수정/삭제 버튼 | `canEdit` / `canDelete` 가 true일 때만 노출 |
| 로그인 시 | 토큰을 함께 보내야 `canEdit`이 정상 계산되고 조회수도 증가 |

⚠️ `board`가 이름 문자열이라 **게시판으로 돌아가는 링크를 만들 수 없다**. 브라우저 뒤로가기나 라우트 파라미터로 boardId를 유지할 것.
⚠️ `author`도 닉네임 문자열이라 작성자 프로필 링크 불가.

### FR-4.3 작성

| 항목 | 내용 |
|---|---|
| API | `POST /api/post/{boardId}/new` (`multipart/form-data`) |
| 파트 | `post`(JSON Blob) + `images`(파일 0~5개) |
| 검증 | 제목 **5~200자**, 본문 필수 |
| 이미지 | 최대 5장, 각 2MB, png/jpg/jpeg/gif/webp |
| UI | 드래그앤드롭 + 미리보기 + 개별 제거 + 순서 = 전송 순서 |
| 성공 | 200 → 상세 페이지로 이동 |

`Content-Type` 헤더를 직접 설정하지 말 것 (boundary 자동 생성).
구체적 코드는 [[API-Post]] 참조.

### FR-4.4 수정

| 항목 | 내용 |
|---|---|
| API | `PUT /api/post/{id}/update` (JSON) |
| 수정 가능 | 제목, 본문 **만** |
| 🚧 불가 | 이미지 추가/삭제/순서 변경 — API 미지원 |

수정 화면에서는 기존 이미지를 **읽기 전용**으로 표시하고 "이미지는 수정할 수 없습니다" 안내를 넣는다.

### FR-4.5 삭제

`DELETE /api/post/{id}` → 확인 다이얼로그 → 목록으로.
응답은 JSON이 아니라 plain text `"ok"` → `res.json()` 호출 금지.

⚠️ 댓글이 달린 게시글은 FK 제약으로 삭제가 실패할 수 있다 (500/400). 에러 메시지를 표시할 것.

## 5. 댓글 (FR-5)

### FR-5.1 목록

| 항목 | 내용 |
|---|---|
| API | `GET /api/comment/post/{postId}/list?page=&size=&sort=` |
| 구조 | 최상위 댓글 페이징 + `children`에 대댓글 전부 |
| 정렬 | 기본 최신순. 오래된 순이 자연스러우면 `?sort=createdAt,ASC` |
| 삭제된 댓글 | `deleted: true` → 회색 처리, 답글·수정·반응 버튼 숨김 |
| 반응 | `likeCount` / `dislikeCount` / `myReaction`이 각 댓글·대댓글에 포함됨 |

`page.totalElements`는 **최상위 댓글 수**다. "댓글 N개" 표시 시 주의.

### FR-5.2 작성 / 대댓글

| 항목 | 내용 |
|---|---|
| API | `POST /api/comment/post/{postId}/new` |
| 최상위 | `{ content }` |
| 대댓글 | `{ content, parentId }` |
| 제한 | 1000자, **깊이 2단계까지** |
| 대댓글의 대댓글 | 400 `CANNOT_REPLY_TO_REPLY` → 답글 버튼을 대댓글에는 노출하지 않는다 |
| 작성 후 | 목록 재조회 권장 (응답만으로 트리 재구성 어려움) |

### FR-5.3 수정

| 항목 | 내용 |
|---|---|
| API | `PUT /api/comment/{id}` (댓글 ID) |
| 요청 | `{ content }` — 1000자 제한 |
| 권한 | 작성자 본인만 |
| 응답 | `CommentResponse` — 기존 반응 수치가 유지된 채로 반환된다 |

삭제된 댓글을 수정하려 하면 400 `CANNOT_EDIT_DELETED`. UI에서 삭제된 댓글의 수정 버튼을 숨긴다.

### FR-5.4 삭제

`DELETE /api/comment/{id}` → soft delete → 목록에서 `"삭제된 게시글입니다"`로 표시된다.

### 🚧 FR-5.x 내 댓글 판별

응답에 **작성자 ID가 없다**. 닉네임 문자열 비교가 유일한 수단이며 중복 닉네임에서 오작동한다.
서버에 `authorId` 또는 `canEdit`/`canDelete` 추가를 요청할 것.

## 7. 반응 (FR-7)

게시글·댓글 모두 반응 등록과 **조회**가 동작한다. 요청/응답 형식은 동일하다.

| 대상 | API | 비고 |
|---|---|---|
| 게시글 | `POST /api/post/{postId}/reation` | ⚠️ **경로 오타** `reation` |
| 댓글 | `POST /api/comment/{commentId}/reaction` | 철자 정상 |

| 항목 | 내용 |
|---|---|
| 요청 | `{ "type": "LIKE" \| "DISLIKE" }` |
| 응답 | `{ likeCount, dislikeCount, myReaction }` |
| 토글 | 같은 타입 재요청 = 취소 (`myReaction`이 null이 됨) |

### 초기 상태 조회

**별도 요청이 필요 없다.** 조회 응답에 이미 포함되어 있다.

| 화면 | 필드 |
|---|---|
| 게시글 상세·목록 | `PostDTO.like` / `disLike` / `myReaction` |
| 댓글 목록 | `CommentResponse.likeCount` / `dislikeCount` / `myReaction` |

`myReaction`을 받으려면 **조회 요청에도 `Authorization` 헤더를 실어야 한다.**
개수(`like`/`likeCount`)는 비로그인에서도 내려온다.

### UI 주의사항

- 토글이므로 같은 버튼을 다시 누르면 **취소**된다 (`myReaction`이 null이 됨)
- 연타 시 상태가 뒤집히므로 요청 중에는 버튼을 비활성화
- 삭제된 댓글에도 반응이 등록된다 (서버가 차단하지 않음) → UI에서 버튼을 숨길 것
- 클릭 후에는 응답 `ReactionResponse`로 해당 항목만 갱신하면 된다(전체 재조회 불필요)

## 8. 알림 (FR-8)

| 기능 | API |
|---|---|
| 안 읽은 개수 (헤더 뱃지) | `GET /api/notify/unreads` → `{count}` |
| 목록 (드롭다운) | `GET /api/notify/list?page=0&size=10` |
| 읽음 처리 | `PUT /api/notify/{id}/read` |

### 실시간성

**서버 푸시(SSE/WebSocket)가 없다.** 폴링으로 구현한다.

```ts
// 30초 주기, unreads만 폴링 (COUNT 쿼리 1회로 가볍다)
setInterval(fetchUnreadCount, 30_000);
```

목록은 드롭다운을 열 때만 조회한다.

### 알림 클릭

`postId`로 게시글 상세로 이동 + 읽음 처리.
⚠️ `postId`/`commentId`는 FK가 아니므로 **삭제된 게시글을 가리킬 수 있다** → 404 처리 필요.

### 🚧 미지원

- 전체 읽음 처리 (개별 호출 반복으로 대체 가능하나 비효율)
- 알림 삭제
- 좋아요 알림

## 9. 공통 UI 요구사항

### FR-9.1 에러 처리

| 상태 | 처리 |
|---|---|
| 400 | 폼 에러 표시. `INVALID_INPUT`은 필드 정보가 없으므로 **클라이언트 검증 필수** |
| 401 | 토큰 재발급 1회 시도 → 실패 시 로그인 이동 |
| 403 | "권한이 없습니다" 토스트 |
| 404 | "삭제되었거나 존재하지 않습니다" |
| 409 | 폼 필드에 중복 안내 |
| 500 | 일반 에러 토스트 + 재시도 |

응답 바디에 `code`가 없을 수도 있다 (핸들러 미등록 예외) → 방어 코드 필요.
→ [[API-에러코드]]

### FR-9.2 로딩 / 빈 상태

- 목록: 스켈레톤
- 버튼: 제출 중 비활성화 + 스피너 (중복 제출 방지 — 특히 반응 토글)
- 빈 목록: "아직 게시글이 없습니다" + 작성 CTA

### FR-9.3 인증 상태에 따른 UI

| 상태 | 노출 |
|---|---|
| 비로그인 | 목록/상세 조회만. 작성·댓글·반응 버튼은 로그인 유도로 |
| 로그인 | 전체 기능 + 알림 뱃지 |
| 작성자 | `canEdit`/`canDelete`로 수정·삭제 버튼 |

### FR-9.4 반응형

모바일 우선. 게시글 작성 시 이미지 업로드는 모바일 카메라 접근을 고려한다 (`<input capture>`).

## 10. 권장 기술 선택

| 영역 | 권장 | 이유 |
|---|---|---|
| 프레임워크 | React + TypeScript (Next.js App Router 또는 Vite) | |
| 서버 상태 | TanStack Query | 페이징·캐시 무효화·낙관적 업데이트 |
| 클라이언트 상태 | Zustand 또는 Context | 인증 상태만 관리하면 충분 |
| HTTP | fetch 래퍼 (401 재발급 인터셉터 포함) | [[API-클라이언트-가이드]] |
| 폼 | React Hook Form + Zod | 서버 검증 메시지가 빈약하므로 클라이언트 검증이 중요 |
| 스타일 | Tailwind CSS | |

`credentials: 'include'`를 반드시 설정해야 Refresh 쿠키가 오간다.
